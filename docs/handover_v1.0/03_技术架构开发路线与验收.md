# 《寒潮清单》技术方案、开发路线与验收（v1.0）

> 面向另一位开发 Agent 的工程执行建议。当前只有策划文件和视觉参考，没有已实现项目。本文件描述**如何开发**，不是声称已经完成。

## 1. 选型结论

### 首选

**Godot 4.7.2 stable（或 4.7.x 当前最新稳定补丁） + GDScript + 2D 节点系统。**

- Godot 官方支持 TileMapLayer、AnimatedSprite2D、AnimationPlayer、2D 物理与 UI 控件；本项目需要场景切换、像素人物、可交互货架和网格摆放，使用一体化引擎更直接。
- Windows、macOS、Linux 本地导出是主要目标；Godot 4 提供 HTML5 导出，网页使用 Compatibility 渲染、单线程导出更容易部署。浏览器兼容仍须实际测试。
- **不用 C#**：Godot 4 C# 项目存在网页导出限制；GDScript 更适合此项目的轻量游戏脚本。
- 不需要 Node.js 后端、数据库服务器、登录系统、云渲染、AI API 或玩家隐私收集服务。

**官方资料**：

- Godot 稳定版本：https://godotengine.org/download/windows/
- 官方 2D 动画：https://docs.godotengine.org/en/stable/tutorials/2d/2d_sprite_animation.html
- TileMapLayer：https://docs.godotengine.org/en/4.6/classes/class_tilemaplayer.html
- Web 导出：https://docs.godotengine.org/en/4.7/tutorials/export/exporting_for_web.html
- 像素比例/整倍数放大：https://docs.godotengine.org/en/stable/tutorials/rendering/multiple_resolutions.html
- 存档示例：https://docs.godotengine.org/en/stable/tutorials/io/saving_games.html

### 备选但不优先

| 方案 | 何时考虑 | 本项目评价 |
|---|---|---|
| Phaser + TypeScript + Vite | 只追求网页/移动浏览器试玩、团队非常熟悉前端 | 也可实现，但需自建较多剧情/建造编辑与存档体系；技术方向会明显变化 |
| Unity 2D | 开发 Agent 已有成熟 Unity 2D 项目或工具链 | 功能可行，但不如轻量 Godot 路线符合“少折腾、快速验证” |
| 原生 HTML/CSS/React | 纯文字经营面板 | 不满足“可移动 2D 角色 + 横版场景和可见建造”的核心体验，不推荐 |

## 3. 模块与责任边界

### 3.1 全局状态 `GameState`

必须由一个权威状态对象管理并进入存档：

```json
{
  "schema_version": 1,
  "day": -7,
  "cash": 48000,
  "ap": 3,
  "health": 100,
  "food": 8,
  "water": 12,
  "fuel": 0,
  "battery_charge": 0,
  "cart_capacity": 12,
  "warehouse_capacity": 30,
  "inventory": {},
  "pending_delivery": [],
  "placed_facilities": [],
  "flags": {},
  "seen_events": [],
  "comfort_score": 0,
  "ending_id": ""
}
```

- 所有花钱、扣材料、消耗 AP、生命损失和添加奖励必须从统一状态操作，先校验后提交。
- 买一箱食物时先形成**物流/库存物品**；拖入有效货架或点击“自动入库”后，才转为可消耗的 `food` 数值，同时货架视觉发生变化。
- 未入库的配送箱不能直接用于夜晚消耗；容量超限时允许先保留在待入库区，但需醒目提示，不会被无提示丢弃。
- 升级设施的实际功能由已安装设备决定，而不是“买下商品就立即获得加成”。

### 3.2 商店系统

- 商店货架数据驱动，不要每个架子写死 `if item == ...`；货架展示可售商品、库存、价格、日期修正、交互范围。
- 购物车订单是一份临时草稿，`add/remove/change_quantity` 不扣现金；`checkout` 才原子性扣现金、扣店库存并生成配送箱。
- `checkout` 同时检查剩余现金、库存、购物车容积和 AP；失败不能扣任何资源。
- 禁止通过反复打开购物车、切场景或读取存档使已购买物品重复生成。

### 3.3 建造和摆放系统

- 用整数网格坐标存储设备位置，不保存屏幕像素坐标；保存 `facility_id`, `cell_x`, `cell_y`, `floor`, `orientation`, `health`。
- 放置前检查同格占用、房间合法性、门与楼梯通行、设备专用区域、物品在库。
- 装好后立即更新仓储容量/热量/用电需求/安全等级；移动已安装设备不能再次获得一次性奖励。
- 仓储物资可以批量显示为堆叠图，库存减少则图随数量减少；不要为每一瓶矿泉水创建常驻物理刚体。
- 先实现一层可布置，再做第二层剖面与楼梯过渡；防止过早制作庞大的房屋编辑器。

### 3.4 日程与资源结算

- `DayManager` 只负责切天、事件日程与 nightly settlement；不要在 UI 按钮里随意减少食物/燃油。
- 固定结算顺序：`当日剧情选择已提交` → `确认设施安装` → `供电来源与燃油` → `实际抗寒` → `居民食物/水` → `生命变化` → `事件解锁/下一天价格` → `自动存档`。
- 每日结算展示可读原因：“电暖器耗电 2/4；燃油 -1；今晚抗寒 27/25；食物 -2；饮水 -2；生命不变”。
- 天气需求值写入 `economy.json` 或明确表格，不写死在几十个独立脚本内。
- 执行相同存档状态的夜间结算应产生一致结果，便于复现 bug。

### 3.5 剧情系统

- 以 `event_id + day + flags + conditions` 唯一触发，已触发记录进 `seen_events`。
- 台词、角色名、选项、资源要求和状态变更使用外部数据配置，不直接散落在动画脚本中。
- 事件选项应有显式 `requirements` 与 `effects`。不满足资源时灰显；必须至少有一个可执行选项。
- 对话快进/重新打开日志仅改变呈现，**不重复执行 effects**。
- 玩家剧情分支选择对后续有可见效果，如 `P04 shared_spare_key` 明确决定 `D05` 门口事件形式。

一个建议的事件数据形状：

```json
{
  "id": "D02",
  "day": 2,
  "once": true,
  "lines": [
    { "speaker": "meng", "text_key": "story.D02.01" },
    { "speaker": "protagonist", "text_key": "story.D02.02" }
  ],
  "choices": [
    {
      "id": "help",
      "label_key": "story.D02.choice_help",
      "requirements": { "food": 2, "water": 2 },
      "effects": [
        { "type": "resource", "name": "food", "delta": -2 },
        { "type": "resource", "name": "water", "delta": -2 },
        { "type": "flag", "name": "meng_helped", "value": true }
      ]
    },
    { "id": "refuse", "label_key": "story.D02.choice_refuse", "effects": [] }
  ]
}
```

## 4. 存档与离线运行

- Godot 官方推荐 `user://` 用于持久可写数据；本项目初期可使用 `user://save_v1.json`，重要状态仅存**数据**，不存直接引用的节点实例。
- 每天结束后**自动存档一个前一日可恢复检查点**，同时支持 3 个手动存档槽；需避免“覆盖前一天检查点”导致失败无法重试。
- 每个存档写入 `schema_version`；加载时做字段缺省与版本迁移，未知字段不致崩溃。
- 为防意外断电，建议先写临时文件、验证后替换正式存档；写失败时显示可读错误，不虚报“已保存”。
- Web 导出单线程、Compatibility 渲染，验证浏览器刷新后存档是否持久。不同浏览器的存储行为不能假设一致；为试玩版提供导出/导入存档备份是加分项。
- 离线打开、无账号、无强制联网，核心游戏不受外部 AI 服务或服务器宕机影响。

## 5. 像素美术制作与素材管理

### 5.1 美术技术规范（先作为目标）

- 基准内部视口 `960×540`，整数倍缩放，最近邻过滤，尽量避免旋转/分数缩放；根据正式 sprite 细节调节最终基准。
- 主角约 80–110 像素宽、160–210 像素高（**初步比例目标，不是必须固定的 asset size**），正常身材、精细衣服褶皱与剪影。
- 地图以 32×32 或 48×48 的像素网格组织；人物/设备和环境像素密度需统一，避免一个角色看起来比一扇门还高两倍。
- 主角最低动画：idle 4 帧、walk 6 帧、shop/interact 4 帧、carry 4 帧；可先用占位 sprite 走通功能。
- 使用 Pixel/Nearest 过滤和 `viewport` / integer scale，保证像素线条一致；中文 UI 可独立调字号，不能因为像素感牺牲可读性。
- 以原创角色 spritesheet、原创建筑瓦片、道具图标和 UI 为最终产物；AI 生成的精细概念图**不能直接当作已经具备动画帧的游戏 sprite**。

### 5.2 画风要点

- 深灰、烟棕、土黄、旧绿；布料磨损、补丁、简单现实服装。
- 室外低温：灰蓝/雪白、玻璃霜、飘雪；安全屋室内：暖黄、橙光、堆满物资、略旧但干净。
- 横版真侧视/建筑正剖面；不做等距斜 45° 视角，更不做 3D 假像素。
- 参考人物图用于艺术方向，不直接沿用原人物面部、服装组合、图像素材到商业版本。建立原创主角设定卡与版权/授权记录。
- 动态可见反馈优先级：购物车变满 ＞ 仓库变满 ＞ 加固门安装 ＞ 暖灯亮起 ＞ 暴雪增强 ＞ NPC 门外求助。

### 5.3 素材获取与生成

- 手工精修工具可选 LibreSprite、Aseprite、Krita；最终全部以统一分辨率的 PNG sprite sheet 和 atlas 导入。
- AI 生成可用来做**气氛参考和构图草稿**，必须经像素美术清理、尺寸/帧数对齐，才可进正式资产。
- 每张导入资源记录来源与授权；音效和字体也需许可。不要从在售游戏截图中抠图、复制角色立绘或直接爬取素材。

## 6. 黑客松与 AI 展示方式

用户希望未来拿游戏参加比赛，但**目前尚未指定某场赛事**。不同赛题可能强制工具、AI API、模型或开源协议，不得假定已符合。

### 通用 48 小时演示切片

1. 20–40 秒重生剧情（能跳过）。
2. 2–3 分钟可操作商店：推车、放入货品、结账。
3. 2–3 分钟回家：自动/拖拽入库，安装货架与取暖器，屋内发生可见变化。
4. 1–2 分钟跳到 D0：外面暴雪，供暖结算，门外 NPC 发来求助，做一次有成本的选择。
5. 30 秒统计：生存成功、房间变化、资源结余，展示“游戏真的可玩”。

### 如果赛事明确要求 AI 原生能力

**可选模块：智能采购顾问**，不影响离线基础版本：读入确定性的 `天气预测、库存、资金、房间设施`，给出三种风格的推荐采购清单及理由（保守、平衡、豪赌）；所有实际价格、数量和结算由本地引擎规则校验。若选用真正模型，应明确模型来源、API 权限、费用、缓存、敏感信息和错误回退；**没有调用模型的规则推荐器不能冒充“AI 大模型功能”**。不要把实时文本生成用作可无限刷资源的工具。

## 7. 开发阶段与交付门槛

| 阶段 | 交付目标 | 验收条件 |
|---|---|---|
| P0 工程底座 | Godot 工程、启动菜单、统一像素相机、测试/日志 | 本地启动不卡死；基本分辨率正常；无缺失素材崩溃 |
| P1 基础移动 | 2D 横版超市和安全屋、角色可移动、货架可交互 | 键盘移动、碰撞、E 交互、回家、重进场景都工作 |
| P2 核心购物 | 商品表、购物车、结账、配送箱、入库、现金和容量规则 | 数额正确；钱不够失败不扣款；购买物品能真实显示到安全屋 |
| P3 核心建设 | 网格摆放、货架、门、取暖器、发电机、建筑反馈 | 不能重叠/堵门；房间外观变化；属性从已装设施计算 |
| P4 日程生存 | AP、切天、资源消耗、温度、电、失败及前日重试 | 有一条完整可失败、可重试的日循环；结果可解释 |
| P5 故事纵切 | P00、P01、D00、D01、D02，选择影响后续 | 玩家完成开场、购物、建造、风雪、求助，得到可见反馈 |
| P6 第一季 | 全事件、3 商店、两层剖面、全部结局 | 从 D-7 到 D+7 可通关且有存档；不同结局均可实测 |
| P7 打磨发布 | 美术统一、动画、音效、教程、导出、bug 修复 | Windows 包可运行；Web 试玩在目标浏览器实际验证 |

**优先级**：先完成 `P0–P5` 的真正 playable vertical slice，暂不画完所有场景；用户确认手感后再扩展 `P6–P7`。

## 8. 技术验收测试清单

### 购物与经济

- [ ] 同一件商品在货架→购物车→结账→配送→仓库只有一条所有权路径。
- [ ] 钱不足、容量不足、店无库存、日期限购时交易拒绝且无副作用。
- [ ] 撤销购物车商品、取消建造、切换地图不会丢物资或重复退款。
- [ ] 灾前第 -3、-1 天价格变化正确，商店限购提示清楚。

### 设施与生存

- [ ] 未安装的发电机不能供电；无燃油时发电机不能自动发电。
- [ ] 电网断电后实际电量与供暖结算正确，供暖加值不会叠加错误。
- [ ] 货架容量提升仅发生一次；移动货架不能刷容量。
- [ ] 食物/水不足会按规则损失生命，负库存不可能出现。
- [ ] 同一份存档重复计算得到一致的最终生命与资源。

### 剧情与存档

- [ ] `shared_spare_key` 真假分别演示 D05 两版本；`chen_helped` 真假演示 D03 两版本。
- [ ] 任何选项资源不足时仍有可选退路，剧情不锁死。
- [ ] 退出、重启、加载后房间/配送/日期/事件/旗标完全一致。
- [ ] 已读剧情快进不重复扣/加资源，过夜不能一键多次提交。
- [ ] 四个结局由可重放测试存档覆盖；失败后前日回滚工作。

### 产品品质

- [ ] 游戏明确的“新游戏/继续游戏/设置/退出”。
- [ ] 音量/字幕、键位说明、已读对话快进、暂停及任务目标完整。
- [ ] 字体可读、非 16:9 屏幕安全区、像素显示无不规则模糊。
- [ ] Windows 目标机实际试玩完整纵切；网页试玩能在 Chrome/Firefox 加载并保存测试数据。
- [ ] 提供启动说明、版本号、已完成/未完成清单和已知问题。

## 9. 交付给用户时应包含

- 可运行游戏包（Windows 优先），不是只有源码或录屏。
- 可打开的完整 Godot 工程（含必要美术资源或合法占位资源）。
- 实际演示 GIF/视频或截图：购物、入库、建筑变化、暴雪夜晚、分支对话。
- 一页试玩说明和操作表；至少一个通关存档及一个测试分支存档。
- bug/未实现清单；下阶段推荐事项，供用户选择。

## 10. 技术决策记录

| 议题 | 决策 | 原因 |
|---|---|---|
| 2D vs 3D | **2D 横版** | 用户明确要求，减少模型、动画和交互工程负担 |
| Godot vs Web 框架 | **Godot 4.7.x + GDScript** | 更适合横版角色、建造、动画和本地单机状态 |
| 末日重生 | **开头一次** | 与短剧剧情相符，玩家不必反复丢失建设成果 |
