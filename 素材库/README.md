## 一、最关键的三条规则

1. **本目录与游戏运行时完全隔离。** 根目录的 `.gdignore`（空文件）让 Godot 在文件扫描时整棵跳过。
   **禁止**任何游戏脚本写 `res://素材库/...`，也禁止把本目录的图片当作 `assets/` 的替代品。
   正式运行资源继续放在 `assets/`、`scenes/`，且只能来自审核通过、有批准记录的素材。
2. **概念图 ≠ 可用素材。** 这里允许存在概念图、参考图、角色设定、分镜、动画预览、废弃版本、多版本并存；
   只有台账中 `审核状态 = 运行时可用` 且填了 `对应运行时资源路径` 的条目才允许被游戏引用。
   「已通过设定审核」只说明美术方向定了，**不代表**已经能跑在游戏里。
3. **现有文件只复制、不移动不删除。** 原图继续留在 `assets/reference/` 与 `docs/handover_v1.*/`；
   本库只放一份带 ART_ID 的副本，用于浏览与讨论，避免重复复制产生冗余。

## 四、台账状态定义

`素材台账.csv` 里有两个容易混淆的字段，必须分开理解：

| 字段 | 取值 | 含义 |
|---|---|---|
| `审核状态` | `概念草案` / `待审核` / `已通过设定审核` / `正式素材制作中` / `运行时可用` / `已弃用` | 生命周期主状态，决定**能不能进游戏** |
| `制作状态` | `未开始` / `概念绘制` / `像素精修` / `引擎试用` / `已交付` / `不适用` | 产线进度，与审核结果无关 |

`运行时可用` 是**结论，不是标注**。只有同时满足下面三条，才允许写这个状态：

1. `对应运行时资源路径` 非空且指向 `assets/` 内的真实文件；
2. 该路径下的文件**确实存在**（克隆后也在）；
3. 已通过验收并在 `制作与修改说明` 里留下批准人、日期、任务编号。

缺任何一条，条目都必须保持非运行时状态。`tools/check_artlib_page.mjs` 会逐条核对这三项，
并用**白名单**约束「谁可以标运行时可用」：任何新增都必须在脚本里显式加一条，越权即验收失败
（CORE-001B 之前是断言「全库 0 条」，现在改为白名单）。

## 五、从素材库进入正式资源的流程

0. **先查号**：在 `ID登记表.md` 里确认这条内容是「已有条目补版本」还是「新开条目」；
   新开就从对应前缀的「下一可用号」顺延，并在 `ID登记表.csv` 先登记，再动文件。
1. 在预览页 / 台账里选中一个版本，记录 `素材 ID + 版本号`。
2. 由用户或总策划**明确批准**（在 `制作与修改说明` 写批准人、日期、任务编号）。
3. 制作或精修出符合 `docs/开发说明.md` 规格的运行时资源，放进 `assets/` 对应分类。
4. 在台账填入 `对应运行时资源路径`，确认文件存在，把 `审核状态` 改为 `运行时可用`。
5. 之后 Godot 才能引用该文件；`.gdignore` 保证素材库本体永远不会被打进包。

**截至 2026-11-10（VIDEO-FINALIZE-001），有 14 条走到第 5 步**（白名单见 §四）：
角色 r10/r11/r12 三段 512×704 高清动画、购物车三档与分层四件、四层货架、商品 r02 两套尺寸。
它们在 `assets/` 下都有真实文件，台账的 `对应运行时资源路径` 指向它们。
其余条目仍停在概念 / 待审核，运行时路径为空，不得引用。
场景素材（`ART_SCENE_*`）当前仍处于设定审核通过阶段，后续由美术总监（ChatGPT）在「场景制作」分支按批次交付正式切片与规格。

## 五之二、每条素材的三个独立事实（CLEAN-001 起）

以前只有一个 `审核状态`，容易被读成「这条到底好不好」。实际上三件事互相独立，
`TASK-ARTLIB-CLEAN-001` 把它们拆成三列，预览页也分三条轴展示：

| 列 | 取值 | 回答的问题 |
|---|---|---|
| `审核状态`（原有） | 概念草案 / 待审核 / 已通过设定审核 / 正式素材制作中 / 运行时可用 / 不予通过 / 已弃用 | **能不能进游戏** |
| `视觉评价`（新增） | 认可 / 待优化 / 未评价 / 不适用 | **美术质量满不满意** |
| `使用状态`（新增） | 正式使用 / 回退保留 / 未使用 | **游戏里现在有没有在用它** |

历史反例是 `ART_CHAR_001 r09`（已删除）：它曾是「运行时可用 + 正式使用 + 视觉待优化」三句同时为真，
正是这条反例促成了三轴拆分。现在 r09 不在了，但**三轴模型保留** ——
将来任何一条动画接进来，都要分别回答这三个问题，不要用一个标签概括。

另外三列是归档与排版用的：

| 列 | 用途 |
|---|---|
| `动作分组` | 角色按动作归档：外观设定 / 待机 / 普通行走 / 推购物车 / 反向拉车 / 搬运 / 其他动作；非角色填 `不适用` |
| `归档标记` | `是` = 仅作历史追溯，不再参与后续制作；这类条目不得有运行时路径 |
| `动画帧序列` | 多帧动画的帧文件 glob（相对 `素材库/`）。**帧文件不单独登记 ID**，归属到父动画行 |
| `参考用途` | 该条目作为 AI 视频参考图时归属的动作；多个动作用竖线分隔 |

这六列的写入由 `tools/artlib_curate.py` 统一负责（幂等，带 `--check` 只比对不写），
**不要手工改 CSV 的这几列**。

## 六、离线预览页

双击 `素材库/美术总览.html` 即可。数据内嵌在 HTML 里，缩略图在 `.thumbs/`，全部走相对路径，
不需要 Node、Python、本地服务器或网络；`file://` 下也能正常工作。

新增素材或改了台账后，运行一次索引生成脚本重建页面：

```bash
python tools/build_artlib.py
```

脚本会：读取 `素材台账.csv` → 为有图片的行生成缩略图 → 为多帧动画生成 `.thumbs/anim/*.gif`
→ 重新生成 `美术总览.html`。数据与渲染分离，扩展到数百条也只是多几行 JSON。

页面结构与筛选（TASK-ARTLIB-CLEAN-001 重做）：

| 区域 | 内容 |
|---|---|
| 顶部三个视图 | **素材**（全库网格）/ **AI 视频参考图**（按动作聚合）/ **动作缺口**（已确认未交付项） |
| 左栏 · 分类 | 角色 / 场景 / 物品与家具 / 界面 / 特效与动画 / 世界观与剧情 |
| 左栏 · 角色动作 | 外观设定 / 待机 / 普通行走 / 推购物车 / 反向拉车 / 搬运 / 其他动作 |
| 左栏 · 状态标记 | 已确定外观设定 / 已通过技术验收 / 当前游戏使用中 / 视觉质量待优化 / 待审核 / 历史归档 / 不予通过（**可多选叠加**） |
| 灯箱 | 大图、版本对照（同 ID 多个版本时并排）、序列帧播放器（真 alpha，按台账 FPS）、预览 GIF、库内副本 / 原始来源 / 运行时资源三个入口、制作与修改说明 |
| 搜索 | 素材 ID、名称、分类、角色、动作分组、视觉评价、说明全文 |

状态标记是**多标签**：同一行可以同时是「已通过技术验收 + 当前游戏使用中 + 视觉质量待优化」，
现状：角色没有任何在用的动画，"视觉质量待优化"与"当前游戏使用中"都归零。
这正是三轴模型的作用 —— 缺一条就少一个事实，不会被"看起来通过"掩盖。

### 页面之外的两条校验命令

```bash
python tools/audit_artlib.py        # 台账 ↔ 磁盘 ↔ assets/ ↔ ID 登记表 ↔ 文档链接 交叉审计
node tools/check_artlib_page.mjs    # 页面行为验收（需先开带 --remote-debugging-port 的浏览器）
```

`audit_artlib.py` 覆盖：库内文件存在性、尺寸与台账是否一致、运行时路径是否在 `assets/`、
归档条目有没有偷留运行时路径、`美术设定集/` 里有没有未登记文件、`assets/` 里有没有无法归属的孤儿文件、
`.thumbs` 与台账条数是否对齐、`素材库/**/*.md` 里的相对链接是否死链、四个动作的 AI 视频参考图是否齐全。
